Confrontation indépendante · free-gemini-api v3.5.7

« Traces, Observabilité et Benchmarking Agentique » — ce que la synthèse retient, ce qu'elle déforme, ce qu'elle invente

J'ai confronté la synthèse critique du rapport (docs/recherches/Traces-Observabilite-Et-Benchmarking-Agentique.md, 412 lignes, 9 264 mots) au document source et au code Go réel. Chaque affirmation ci-dessous a été rejouée : DDL exécuté dans SQLite 3.37.2, constantes relues dans les fichiers, identifiants arXiv résolus.

Verdict. La synthèse est fidèle sur le fond — les quatre « révélations » sont réelles, les chiffres de The Complexity Trap sont exacts au dixième près, et le DDL s'exécute vraiment. Mais elle surestime la maturité opérationnelle de trois chantiers : elle présente comme « actionnables » des éléments qui n'ont ni producteur, ni consommateur, ni adaptation au modèle réellement utilisé. Trois points sont factuellement faux ou non étayés.

01Les affirmations qui tiennent (vérifiées)

Ce ne sont pas des paraphrases plausibles : je les ai confirmées ligne par ligne.

EXACT

Le verrou Task [40] → Chat [0] du banc d'essai

C'est la révélation la plus opérationnelle, et elle est juste. ResolveModelForRequest requalifie bien une requête porteuse d'outils vers le modèle Chat de la même famille, et benchmark_matrix.sh ne pose jamais l'en-tête d'opt-in.

Preuve : chat_service.go:191-205 — if hasTools && !TaskModeAllowedForTools(c) → chatModelForTaskRequest ; :684 passe len(req.Tools) > 0. Le banc n'invoque que opencode run --model, aucun en-tête.

Nuance Le bras gemini-4-argon (AppMode 0) n'était pas concerné ; seuls les deux alias -task l'étaient. La conclusion « Chat contre Chat » vaut pour eux, pas pour la matrice entière.

EXACT

La dette foreign_keys du DSN et le failure mode RGPD

Le DSN n'active effectivement pas les clés étrangères, et je l'ai mesuré : sans ce pragma, tous les ON DELETE CASCADE sont décoratifs. Mais la conclusion « les purges ne cascadent pas » est inversée pour le périmètre actuel.

Preuve : db.go:47 — ?_pragma=journal_mode(wal)&...&_pragma=temp_store(memory). Aucune de ces tables n'existe aujourd'hui dans db.go ; PurgeExpiredData et DeleteConversation suppriment par WHERE explicite, donc ils fonctionnent déjà.

Le risque réel est futur : dès que le schéma proposé sera adopté, une purge RGPD laissera des lignes orphelines dans agent_turns et tool_call_spans tant que le pragma manque.

EXACT

Le masquage d'observations n'a aucune notion de palier de réflexion

Confirmé, et c'est bien un angle mort. observation_masker.go ne contient ni thinking, ni tier, ni reasoning : il compacte les observations anciennes en gardant les 4 plus récentes, sans distinguer les erreurs.

Preuve : fichier entier relu — zéro occurrence de « thinking » ; signature maskOldToolObservations(messages, maxRecentKept, sizeThresholdBytes, overheadBytes). Appel unique chat_handler.go:733, avec defaultObservationMaskKeepRecent = 4.

Mais « préserver les erreurs récentes » est déjà partiellement vrai : les 4 dernières observations échappent au masquage. Le vrai chantier est de détecter les erreurs, ce que le masker ne sait pas faire.

EXACT

Le DDL s'exécute — 6 objets, 0 erreur

J'ai extrait les 229 lignes du bloc et les ai passées à sqlite3 3.37.2 : les 5 tables STRICT, les index partiels et la vue v_session_telemetry_summary se créent sans erreur, avec les colonnes GENERATED.

Preuve : sqlite3 ddl2.db < ddl.sql → DDL OK ; .tables liste agent_sessions, agent_turns, tool_call_spans, turn_anomalies, benchmark_trials + la vue ; SELECT count(*) FROM v_session_telemetry_summary → 0.
EXACT

Les chiffres de The Complexity Trap

Ce n'est pas une citation approximative. J'ai relu la Table 1 de la v3 : le message de la synthèse est numériquement exact.

Gemini 2.5 Flash (thinking) : Raw 40,4 % → Observation Masking 36,4 % (-9,9 %, p = 0,0406) → LLM-Summary 31,4 % (-22,3 %). Qwen3-Coder 480B : +2,6 % à -52,7 % de coût. Gemini non-thinking : +8,5 % à -56,1 %.

02Les affirmations fausses, extrapolées ou non étayées

C'est ici que la synthèse dépasse le document — et parfois le contredit.

FAUX

« Remplacer la formule naïve (c/n)^k par les estimateurs de Yao »

Le script ne calcule nulle part (c/n)^k. Il exige une conjonction stricte : passes == RUNS. Présenter cela comme un correctif d'estimateur est une transposition pure : il n'y a aucun estimateur à corriger, mais un protocole à construire.

Preuve : benchmark_matrix.sh:343-350 — if [ "$total" -eq "$RUNS" ] && [ "$passes" -eq "$RUNS" ]. Aucun awk de puissance, aucune division c/n.

La formule sans biais elle-même est correcte, et l'exemple numérique est juste (n=5, k=3, c=3 → 1/10 = 10 % contre 21,6 %). Le problème est de l'énoncer comme une correction d'un existant qui n'existe pas.

FAUX

« LoopRoute : abaisser le seuil de 3 à 2 dès que le dernier appel est en erreur »

Techniquement infaisable tel quel : DoomLoopTracker n'a aucune connaissance du résultat d'outil. Il n'enregistre que nom + empreinte d'arguments + booléen de mutation. Le seuil doomLoopRepeatWarnThreshold est une constante globale, pas une fonction du contexte.

Preuve : doom_loop.go:67 — RecordToolCall(name, argsJSON string, isMutation bool). session_transcripts.go:312 — appelé depuis recordSessionToolCalls, qui ne voit que les appels émis. Les résultats d'outils sont traités ailleurs (recordSessionToolResultOutcome, ledger).

Il faudrait ajouter un champ d'état au tracker et un canal de retour — un chantier, pas un réglage de constante.

FAUX

« Le DDL s'ajoute directement à côté des tables existantes (messages, media_generations, request_logs, accounts) »

Le DDL est exécutable isolément, mais il rejette des valeurs que le code produit réellement. Je l'ai testé : le schéma et le producteur se contredisent sur deux axes.

  • replay_reason n'admet pas 'none', alors que emitTurnSummary normalise toute valeur vide en "none". Mon INSERT a échoué avec CHECK constraint failed (exit 19).
  • Le CHECK exige 'delta', mais planSessionTurnWithReason ne retourne jamais ce label pour un delta : reason n'est renseigné que dans la branche reset().
  • turn_class admet stream_stalled et empty_thought_only, que classifyTurnOutput ne produit jamais (ces états sont des drapeaux/colonnes séparées).
Vérifié : INSERT ... replay_reason='none' → exit 19 ; replay_reason='delta' → exit 0 ; turn_class='stream_stalled' → exit 0. Le classifieur réel renvoie l'un de refusal, untagged_mutation, schema_invalid, tool_call, incomplete, greeting, pseudo_report, unbacked_completion, ok.

Rien de bloquant — mais cela confirme que « intégré » est prématuré : il faudra une passe d'alignement schéma ↔ producteurs, et un test qui insère les valeurs réelles.

EXTRAPOLÉ

Le -9,9 % présenté comme valant pour Gemini 4 / mode thinking

La mesure porte sur Gemini 2.5 Flash via l'API Vertex, avec un budget de réflexion plafonné à 800 tokens pour raison de coût. Le rapport source le dit correctement ; la synthèse écrit « Gemini 2.5 Flash en mode thinking » dans le constat, mais l'applique ensuite à « votre proxy » sans aucune clause de transposition.

Le rapport ne mentionne « 2.5 Flash » que 3 fois, toujours correctement. Aucune mention d'un protocole de réplication sur gemini-4-* : c'est un résultat à reproduire localement, pas un acquis.

Aggravant : c'est le seul modèle de l'étude dont le masquage régresse. Les quatre autres configurations s'améliorent ou sont neutres. Généraliser l'angle mort à l'ensemble du proxy est donc un pari, pas une conclusion.

INCOMPLET

« Validation formelle des invariants I1–I8 »

Le titre promet une validation des huit invariants. Le corps n'en discute que quatre (I4/I5, I6 via E_FAKE_QUOTA, I7) et en cite trois nommément. I1, I2, I3 et I8 — continuité de session, retry sur greeting, absence de JSON d'outil dans CleanText, budget mémoire LRU — ne sont jamais mentionnés.

Comptage sur le fichier : I1 → 1, I6 → 1, I7 → 2, I2/I3/I4/I5/I8 → 0 occurrence. Le tableau « validation formelle » ne couvre donc pas son titre.
FAIBLE

« 90 sources académiques et industrielles »

Il y a bien 90 entrées, et les identifiants que j'ai résolus existent (y compris les très récents 2607.x / 2611.x). Mais la composition est plus hétérogène qu'annoncé :

  • 35 arxiv.org, 9 huggingface.co (fiches de datasets, pas des publications), 9 github.com (dépôts).
  • Une dizaine de domaines de blogs ou d'agrégateurs — agentswarms.fyi, santageai.com, iotdigitaltwinplm.com, hypeart.ai — sans garantie de revue.
  • Deux références d'ingénierie (« Demystifying Evals », guide Anthropic) ne figurent pas dans les sources listées.
Ce n'est pas une faute — mais « 90 sources académiques et industrielles » survend une bibliographie où le quart est de la documentation produit.

03Ce que la synthèse omet et qui change les priorités

OMIS

Le double TTFT n'a aucun producteur

C'est l'omission la plus lourde. La synthèse présente le double TTFT comme un simple ajout de colonnes. Or aucune instrumentation de première pensée / première réponse n'existe dans le code : ni ttft, ni first_thought, ni first_answer. La ventilation thought_tokens / answer_tokens n'existe pas davantage.

grep -rn "ttft|first_thought|first_answer|thought_tokens|answer_tokens" --include=*.go . → aucun résultat. EstimateTokens ne produit qu'un total.

Le chantier n°1 n'est donc pas « ajouter des colonnes », c'est instrumenter le streaming SSE pour horodater trois fronts (début, premier <thought>, premier texte visible). C'est un travail dans arranger.go/stream_guard.go, pas dans db.go.

OMIS

Aucune donnée de benchmark n'alimente le DDL

benchmark_trials attend un en-tête X-Benchmark-Trial-ID. Cet en-tête n'existe nulle part : ni dans le script, ni dans la liste CORS, ni dans un handler. Le lien entre banc et télémétrie est aujourd'hui entièrement à construire.

Recherche sur *.go, *.sh, .env* → 0 occurrence. security.go:112-126 n'autorise pas cet en-tête en CORS.
OMIS

Le masquage s'exécute AVANT le ledger, et c'est déjà géré

La synthèse présente « vérifier que le masquage ne s'applique jamais aux erreurs récentes » comme une sécurité à ajouter. Le code a déjà la parade, mais par un autre mécanisme : pristineNonSystemMessages est conservé avant masquage et sert à reconstruire le ledger de preuves.

chat_handler.go:722-726 — « Keep the unmasked transcript for the evidence ledger: masking may compact an old tool result past an error marker » ; :850 — recordSessionLedgerFromMessages(sessionKey, pristineNonSystemMessages).

La preuve d'exécution est donc déjà immunisée contre le masquage. Ce qui manque réellement, c'est que le modèle voie encore ses erreurs — pas que le ledger les voie.

OMIS

Un quota de retries et un pipeline d'échec déjà bien plus riches que le tableau

La taxonomie d'échec à 4 couches est excellente, mais elle ignore des signaux déjà exposés qu'elle pourrait consommer sans nouvel instrument : gemini_quarantine_total{kind}, gemini_arranger_repairs_total{kind}, gemini_doom_loop_interventions_total, gemini_ground_truth_directives_total, gemini_upstream_suspected_stop_total.

metrics.go — les cinq compteurs existent et sont déjà alimentés par recordArrangerRepairs, recordTurnClass et le circuit-breaker.

05Ce que je retiendrais, dans l'ordre

  • 1. Le banc d'essai est le seul chantier immédiat. Ajouter X-Allow-Task-Mode-For-Tools: true au bras -task, et remplacer passes == RUNS par pass^k et pass@k avec les formules combinatoires. Les deux sont de vraies corrections, localisées, à faible risque.
  • 2. Instrumenter avant de schématiser. Le DDL est bon mais ne peut rien stocker : pas de TTFT, pas de ventilation de tokens, pas d'en-tête de corrélation. Écrire les tables d'abord reviendrait à créer un schéma vide et à le laisser diverger.
  • 3. Aligner le schéma sur les producteurs. Une fois l'instrumentation faite, tester le DDL en insérant les valeurs réelles de classifyTurnOutput et des raisons de replay — pas seulement vérifier qu'il compile.
  • 4. Le seuil dynamique du doom-loop est un chantier annexe. Utile, mais il exige de faire remonter result_is_error jusqu'au tracker ; à planifier après le banc, pas avec lui.
  • 5. Ne pas activer foreign_keys « pour plus tard ». Le faire au moment où le schéma est adopté, avec un test de cascade ; l'activer seul aujourd'hui ne change rien et donnera une fausse impression de conformité RGPD.
